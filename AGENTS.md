# UH Homes Selections

- A Flask app backed by one master `.xlsx` workspace, in one of two modes chosen purely by environment variables: local (a file beside the app, no accounts, bound to `127.0.0.1`) or hosted (the workspace in Supabase Storage, sign-in required). Default to local; keep both paths working.
- On Windows, run `.venv/Scripts/python.exe app.py` (or add `--port 5001` if port 5000 is occupied; do not stop unrelated services). Install runtime dependencies with `.venv/Scripts/python.exe -m pip install -r requirements.txt`.
- Core verification: `.venv/Scripts/python.exe -m unittest test_workflow test_custom_fields test_hosting test_catalog -v`, `node --check ui.js`, and `.venv/Scripts/python.exe -m pip check`.
- Browser verification: install `requirements-dev.txt`, then run `.venv/Scripts/python.exe -m unittest test_browser -v`. The browser test uses installed Microsoft Edge through Playwright, runs against a temporary workspace, and saves screenshots under `output/`.
- Do not run `build_tracker.py` against the working master workspace; it overwrites it with example data. Tests must use temporary copies of the workspace.
- To point a *local* app at a different workspace file (e.g. a temp copy for a smoke test), set `UH_WORKSPACE` — the path `common.WORKSPACE` reads. `UH_WORKSPACE_NAME` is only the hosted object's name inside the Supabase bucket and is ignored in local mode: a smoke test that sets only `UH_WORKSPACE_NAME` silently runs against — and saves to — the real master beside the app. That exact mistake has contaminated the master twice (restored from git both times; `backups/` also keeps every pre-save copy). Verify the temp file's mtime changes after a test save if in doubt.
- Web edits go through `WorkspaceStore`, which validates headers, detects stale revisions, backs up the existing workspace, and atomically replaces it. Close Excel before saving through the app.
- `WorkspaceStore` owns validation, the `ensure_*` repairs and the price-schedule rebuild; a backend owns only bytes, revisions, backups and history. `LocalBackend` (in `workspace_store.py`, so tests can patch `workspace_store.os.replace`, `workspace_store.workspace_open_elsewhere` and `workspace_store.BACKUP_KEEP`) keeps the file-on-disk behaviour; `SupabaseBackend` is in `supabase_store.py`. Add storage features to the backend interface, not to the routes.
- Hosted saves upload a new immutable `versions/<stamp>.xlsx` object and then advance the single `uh_workbook_state` row with a filtered PostgREST `PATCH`, so the compare-and-swap — not the revision pre-check — decides who wins. If the pointer update fails, delete both the object and its version row so nothing unreachable is offered as a restorable copy. Earlier versions *are* the backups; `backups()` excludes the live revision to match the local folder.
- Local saved copies are ordered by the microseconds in their filenames, never by second-precision timestamps or filesystem mtime: several saves land within one second and "restore the newest copy" must be exact.
- The hosted backend caches the pointer row for `UH_REVISION_TTL` (1s) because the UI polls every 2.5s; a stale read can only cause a rejected save, never a lost one. Never cache in a way that lets a save bypass the compare-and-swap.
- `common.Sheet.set(row, header, None)` is a silent no-op, because openpyxl's `ws.cell(..., value=None)` does not write. Use `workspace_store.put` to clear a cell.
- Talk to Supabase with `requests` over the Storage and PostgREST REST APIs, matching the project's no-heavy-dependencies style; do not add `supabase-py`. Never let a key or a response body reach an error message, a log or an API response.
- Send keys through `auth.key_headers`. The newer `sb_publishable_…`/`sb_secret_…` keys are opaque strings, not JWTs, so they go on `apikey` only; legacy `anon`/`service_role` JWTs go on both `apikey` and `Authorization`. Keep the client's `User-Agent` non-browser-like: Supabase rejects secret keys that look like they came from a browser.
- A half-filled `.env` means "not configured yet", not an error: `settings()` returns `None` so the local app keeps running mid-setup. The dangerous combination — a non-local `UH_HOST` serving a local workspace file, which a redeploy would discard — is refused by `check_exposure()` instead.
- Sign-in is server-side only: `auth.sign_in` posts to Supabase Auth and the browser gets nothing but a signed Flask session cookie, never an access token. The app always reaches Postgres with its own service key. Accounts are created by an administrator (`python auth.py <email>…`, or the dashboard); there is deliberately no sign-up, password reset or email delivery.
- `python supabase_store.py check` is the hosting pre-flight: tables, bucket privacy, seeded workspace, missing variables. Keep it accurate when adding hosting requirements, and keep it free of secret values.
- `deploy_render.py` creates or updates the Render service from `.env`, so settings live in one place. `UH_TRUSTED_HOSTS` must be written after creation, because the hostname is only known then and a wrong value makes every request 400. It must keep sending `numInstances: 1`. Add any new hosted setting to its `COPIED` list, and to `REQUIRED` if the app cannot start without it. It then asks Render for a deploy by name: an environment change rebuilds only when a value actually changed, and a push only while Render's GitHub connection is live, so neither ships a commit reliably. The host once served code three commits old, which rejected the workspace for missing the retired lookup columns that version still required — a stale host and a current workspace is what that class of error looks like. It happened again, twice in one day, with `autoDeploy` reading `yes` the whole time: a corrected footer and then a new column were both live in `main` and absent from the site, so each looked like a bug that had not been fixed. `.github/workflows/deploy.yml` now asks for the deploy from GitHub on every push to `main`, gated on a `RENDER_SERVICE_ID` repository *variable* (a secret cannot be read in an `if`, and a missing variable must skip rather than fail every push) with `RENDER_API_KEY` as a secret. It ships code only; environment values still belong to `deploy_render.py` and `.env`. When a report and the code disagree, check which commit the host is on before reading the code again.
- A 502/503/504 is the host's router, not the app: the hosted workspace is deliberately one process, so a deploy or a restart leaves a few seconds with nothing behind the address, and a save or a poll caught in that gap used to read `Request failed (502)` as if the workspace had refused it. `ui.js`'s `api` retries a *read* through `GATEWAY_WAITS` (0.7s, 2s, 4.5s), which covers the 2.5s poll and every `refresh`. It must never retry a write: `delete` names a row by its number and the editor creates rows, so a second attempt could remove the wrong line item or add a duplicate — the message says the app is restarting and the edit stays held for Save, which already retries. `test_browser.test_a_restarting_host_is_waited_out_rather_than_reported` pins both halves.
- The CSRF token is per-session when signed in and per-process (`TOKEN`) when running locally, both sent as `X-UH-Token`. Signing in clears the session, so any pre-login token must stop working. Add new routes to `OPEN_ENDPOINTS` only if they are genuinely safe unauthenticated.
- `check_exposure()` runs at import and refuses to start when `UH_HOST` is non-local without sign-in, `UH_SECRET_KEY` and `UH_TRUSTED_HOSTS`. Never weaken that: it is what stops a misconfigured deploy from publishing client selections and pricing.
- The hosted app must run as exactly one process (`wsgi.py` with `waitress-serve --threads=8`), because a save rewrites the whole workspace and a second worker would race the first. Scale with threads, never instances.
- There is deliberately no product lookup and no link verification of any kind: no search provider, no `Add from link`, no `Lookup Status`, no `Checked On`, no stale/`Re-check` flag and no `Verified` state. `Product URL` is typed or pasted by the person specifying the home and is simply present or absent. Do not reintroduce a background worker, a search API key, a `/api/selections/<row>/lookup` route or a status column, and do not add a `confirm_verified` argument back to `merge_selection`.
- `Lookup Status`, `Checked On` and `Lookup Notes` on Selections, plus `Links Found`, `Verified` and `Needs Review` on Projects, are listed in `RETIRED_SELECTION_FIELDS` / `RETIRED_PROJECT_FIELDS`. `records` hides them so a workspace saved before they went reads back like one saved after, and `drop_retired_columns` (first step of `WorkspaceStore.save`) deletes them for good. Deleting shifts every column to its right, which openpyxl does not follow through to list validations or hyperlinks, so that function clears both and lets `ensure_validations` and `ensure_product_links` rebuild them from the surviving headers. Lists column B is emptied rather than deleted, because the Yes / No, Client Status and Locations ranges name columns C, D and E by letter. They stay in `common.AUTO_OR_FORMULA` so a stray leftover value cannot make an empty row look occupied before that save happens.
- The only generated documents are the spec sheets (`build_lookbook.build_spec` for PDF, `build_word.build_spec` for Word) and the spec-sheet CSV. The finish-schedule, fillable and PowerPoint builders (`build_lookbook.build`, `build_form`, `build_word.build_fillable`, `build_powerpoint`) remain as command-line tools and are deliberately not reachable from the app.
- The workspace itself is never downloaded or uploaded through the app: there is no `/api/workspace`, no workspace import and no backup/restore route. Earlier copies are still written before every save and restored with `WorkspaceStore.backups()`/`read_backup()`/`import_bytes()` from a script or a test.
- The spec-sheet exports mirror the app's spec-sheet table exactly, column for column: `build_lookbook.SPEC_COLUMNS` is Item, Manufacturer, Model #, Finish / Color, Size / Configuration, Product Link, Qty / Unit, Unit Price and Markup %, and it must stay in step with `SPEC_COLUMNS` in `ui.js`. Its width shares are not free numbers: each one is wide enough to print its own heading on one line, and the link column's share trimmed to what it actually prints - the heading `LINK` over one-word `Link` anchors, via `SPEC_LABELS`'s `Product Link` entry and `link_word()` - its freed share split across the columns whose text wraps, because a wrapped heading reads as two columns — `PRODUCT` over `LINK`. Portrait sets the floor (the same columns in three quarters of the width, with 3pt cell padding instead of 6pt), hiding columns only ever widens what is left, and Word lays the same shares out in metric-identical Arial, so one check covers every export: `test_every_spec_sheet_heading_prints_on_one_line` measures each heading against its column and must stay green if a share is ever trimmed. A share is a starting point, not a cap: `spec_widths` first pins every column at `spec_floor` — heading plus the longest unbreakable text its cells print — then lets the shares divide what is left, so nothing a cell carries is torn in half. `SPEC_ATOMIC` lists the columns whose values count whole (`Model #`, `Qty / Unit`, `Unit Price`, `Markup %`): a model number split even at its own space reads as a typo and a quantity parted from its unit reads as two fields. The count is per value, not per column — a value holding whole while it fits inside `SPEC_ATOMIC_MAX` (a fifth of the page), by its longest word once it does not, so a description-length entry wraps meaningfully at its spaces instead of seizing the sheet, while the prose columns still wrap at spaces on their longest word. `test_a_spec_column_widens_until_its_longest_text_fits_whole` pins both, and the details-box rows never enter the measure — their figures print in fixed band fields, not the table. The sizes those shares answer to are `SPEC_HEAD_STYLE` (7/9.5 bold) for the labels and `SPEC_CELL_STYLE` (9/13) for the line items — a point under the client schedule's 10/13 descriptions, by request — with `SPEC_NOTE_STYLE` (8/10.5) for the notes under the item: the row's `Section` prints there (matching the `.cell-sub` line the spec table shows on screen, so the category is readable in a room-grouped sheet) unless the export is already grouped by `Section` or the Category column was hidden, and the "Not in lookbook" flag follows it. The labels are deliberately smaller than the data they head: the longest of them, `MANUFACTURER`, is what sets a column's minimum width, and at 8pt it took the room an item name needs. A column name too long to fit even that gets a printed label instead — `SPEC_LABELS` shortens `Size / Configuration` to `SIZE / CONFIG` and `Product Link` to `LINK` (cells print the same word through `link_word()`), read back through `spec_heading` — while the CSV keeps the field's full name so a download still imports. `build_word.build_spec` reads all three off those styles instead of repeating the numbers, so the two documents cannot drift. `spec_groups` puts the rows under the heading the view is grouped by, passed as `group` (`Room / Area` or `Section`, validated in `app.py` and sent by `specQuery`), so a download reads like the screen it came from. Reading like the screen also means *in the screen's order*: `spec_export_rows`, the spec CSV and `spec_rows` hand over line items in plain workspace order and must never `schedule_sort` them, because the view is workspace order and dragging a row on the spec sheet writes that order back. Sorting the rows by Location instead moved twelve of thirteen headings and scrambled the rows inside them, so a row dragged into place landed somewhere else in its own PDF; `test_spec_exports_keep_the_order_the_view_shows` pins the CSV, PDF and Word order to the sheet. The view's two group-by chips are By room — `state.specGroup`'s default, and so `group_option`'s and every `build_spec`'s — and By category; grouping the spec sheet by Location was removed by request, so `SPEC_GROUPS` refuses it like any other unknown name. The finish schedule's own `group_sections` still prints Location headings, which is a different function and stays. Mirroring is about columns and order, not rules: the PDF alone rules its column gaps (`spec_table`'s `LINEAFTER`), because eight narrow mostly-empty columns otherwise read as one drifting line; that was asked for in the PDF only, so `build_word.build_spec` keeps its row rules and nothing vertical. Those gaps are secondary structure and must stay the lightest rule on the sheet — 0.2pt against the rows' 0.4 — and they run from the heading rule to the rule that closes the table under the last row (`(0, 1)` to `(-2, -1)`): the foot now carries a 0.5pt rule at the heading's weight, because an open foot read as a row still waiting for its line, and both ends of every gap land on a horizontal. There is still no rule above the headings — a section's own heading rule does that job. `test_the_spec_sheets_column_gaps_are_light_and_close_on_a_row_rule` measures every page of a sheet long enough to split, because reportlab resolves those negative row indices per fragment, so each page closes on its own repeated heading and its own foot rule. One group is deliberately *not* that table: a heading called `PROJECT` (`DETAILS_GROUP`, tested by `is_details_group`) holds the home's own figures — areas, garage size, porch counts — and prints as a short list on open paper rather than a ruled table: pairs of label and figure, `DETAIL_PAIRS` of them across with a real `DETAIL_GUTTER` column between, nothing ruled between the rows, the section heading's own rule opening the block and a single hairline closing it (`spec_details` in both builders). It was ruled like a ledger first — a `field_rule` hairline under every pair, and a hairline of its own laid directly under the heading's rule — so eight areas arrived with five rule heights around them and read as a bank statement; figures ranged on one edge are already a column, so the ink came out and `DETAIL_PAD_Y` of air went in, on screen (`.spec-details-box`) as well as in both documents. `test_the_project_figures_are_not_ruled_like_a_ledger` pins the printed pair: the client band's four field underlines stay the only gold on the sheet, and the box's only hairline is the one under its last row. `detail_parts` splits a figure the way the portal's box does — the `Size / Configuration` cell is the figure, set against the end of its pair through `DETAIL_FIGURE_STYLE`, and every other still-shown column follows as small print under the label, with the joined remainder (`detail_value`, which takes a `skip`) standing in as the figure when that cell is empty. Tiled as band fields instead — a name over its figure, four across, padded for an underline — eight of a home's areas ran a third of the way down the page in white space; `7ae79ab` compacted the portal alone and left both printed copies behind, which is what "why is the design still the same" looked like. Two pairs rather than three because a label has to print on one line to read as a label: measured against those eight figures, three across wrapped five of them in landscape and every one in portrait. A label and its figure share one baseline, and each renderer needs its own nudge to do it — reportlab puts a paragraph's first baseline exactly its font size below the top of its box (`DETAIL_BASELINE`), Word hangs an exactly spaced line from the bottom of its line box (the leading difference) — both read off the styles so the two documents cannot drift. `test_the_project_figures_read_as_a_short_list_not_a_tiled_grid` pins the row count, the shared baselines, the one-line labels and the Word copy's own columns. Those figures answer to the project rather than to a room or a category, so the group is found per row, not per heading: `is_details_row` marks a row whose `Room / Area` *or* `Section` says PROJECT, and `spec_groups` lifts every one of them into a single `PROJECT` group that leads the sheet under either grouping. Grouped by category they used to be filed among the line items under whatever category they carried, so that download had no box at all and the areas read as a few nameless rows in somebody else's table; `test_the_project_figures_lead_the_sheet_grouped_by_category_too` pins the PDF and the Word copy both ways round. `ui.js`'s `specGroups` lifts them the same way through `SPEC_GROUP_FIELDS`, so the screen and the download agree whichever chip is active. The portal draws the same box — `specDetail` inside `.spec-details-box`, two columns of one-line rows that collapse to one on a narrow screen: label left, figure right, the other filled columns as small print — and a figure in it still takes the same inline edits, drag and card reorder as a line item; `test_workflow.test_the_project_group_prints_as_a_details_box_not_a_table` and `test_browser.test_the_project_room_renders_as_a_details_box` pin both surfaces. The sheet's own type hierarchy stands apart from the schedule's: section headings are *tracked*, not letter-spaced - `place`/`Heading`/`section_block` take a `track` in points (`SPEC_HEADING_TRACK` = 1.2, `charSpace` in the PDF, `w:spacing` via `build_word.letterspace` in Word) so `SUITE BATH` prints with a small space after each letter rather than a full space between them; the finish schedule keeps `spaced_caps` because its headings are pinned to the approved template. `SPEC_HEAD_STYLE` inks its labels in `C["dark"]`, not the muted gold of the body furniture, so a column header cannot blend into the 10pt line items it heads; the details box keeps the muted `DETAIL_HEAD_STYLE` on purpose, because those labels *are* the band's. The spec sheet's client band reads its values at 11pt bold (`Band`/`band` take `value_size`/`value_font`), while the schedule's stays at 9pt as the template pins it. The portal mirrors all three: `.spec-table th` is darker and tighter-tracked than the cells, `.spec-card-head h3` sits at a near-tracked .4px, and `.spec-client-fields` inputs take their own larger weight.
- The spec sheet prints landscape or portrait, chosen per download. `build_lookbook.spec_page` is the only place that geometry lives — page size, content width, the body top that stays 96pt below the top edge either way, and the cell padding — so the PDF and the Word copy turn together; `spec_orientation` validates the name, and an unknown one is a 400 through `app.orientation_option` rather than a quiet fall back to landscape. Landscape remains the default in every layer: the builders' own argument, the `--orientation` flag and `ui.js`'s `ORIENTATIONS[0]`. Portrait pads its cells to 3pt instead of 6pt (`SPEC_PAD_X`), because nine columns in three quarters of the width leave the narrow ones barely wider than their own headings even then. The file is named `..._Spec_Sheet_Landscape` / `_Portrait` so both copies can sit in one folder, and the CSV has no page, so the dialog's chips ride only with the Word and PDF links (`docQuery`, remembered in `localStorage` like the hidden columns). `test_workflow.test_spec_exports_print_the_orientation_the_download_asks_for` pins the page sizes, the names and the refusal.
- Every data cell of the *PDF* spec sheet is an editable form field (`SpecFieldCell`, with a blank `Notes` row closing each section), so a downloaded sheet can be typed into; the Word copy and the CSV are plain. A field is a box rather than a column, and the cell both draws its value on the page — for print, and so `extract_text` still reads it — and hands it to the field, so a value longer than its box was clipped by the reader *and* spilled across the cell beside it at once: letters standing outside their boxes, half a finish name lying over the next column, is what that looks like. `spec_field_lines` wraps the value to the room its column was measured for, the box grows `SPEC_FIELD_LEADING` per extra line, and the `multiline` flag goes on so a reader lays the same lines back out instead of re-running them together; the drawn copy uses reportlab's own appearance geometry (`4 * SPEC_FIELD_BW` in, first baseline `fontSize + 2 * SPEC_FIELD_BW` below the top, 1.2 leading) so the two coincide rather than printing as a blurred double. A reader keeps `SPEC_FIELD_INSET` of every field unusable inside its border: the box is drawn that much wider than its cell, half either side, so what a field holds is exactly the room `spec_widths` measured. Charging the columns for it instead — adding it to that function's own padding — pushed the portrait floors past the page width, and the floor scaling that follows tore `Insulation/Drywall` in half. `test_workflow.test_a_spec_sheet_field_holds_its_value_inside_its_box` pins every line inside its box and every box tall enough for its lines, in both orientations. A box is a whole number of lines deep and never deeper (`spec_field_height`): slack is what a reader slices a line along, because it lays its own lines out from the top and clips at the edge, so the old 15pt one-line box left 3pt a 9pt line could not fill and the line below it stood a third of the way into that and was cut off there - which is what a value typed in longer than its box looked like. Edge (PDFium, and so Chrome) steps a 9pt field line by 10.79pt, reportlab's own 1.2 leading to within a rounding, so whole lines here are whole lines on screen; what no height can prevent is a reader scrolling to the caret and clipping mid-line once the text passes the room, which only room answers. `SpecFieldCell.hold` is where the room is decided - the deepest value in the row, because the row is that deep anyway and the rest of its boxes may as well offer the same - and on the editable copy every box opens at `SPEC_FIELD_MIN_LINES` (3) whatever its value needs, so a sentence typed into a cell runs on to a second line and a third inside the column it belongs to. That room is the working copy's alone: the locked copy keeps each box at its own lines and stays the dense one to print, so the editable copy of a long sheet runs about 1.7 times the pages. Auto-sized fields (`0 Tf`) were measured instead of guessed and rejected: Edge shrinks a long value to about 5pt and blows a short one up to 14, and MuPDF ignores auto size altogether and prints 12pt. The sheet goes out as one of two copies, chosen per download: `locked`, which a plain download gives and which carries no fields at all, and `editable`, whose cells are those fields. Locked leads `SPEC_COPIES` — and so `spec_copy`'s default, `build_spec`'s own argument, the `--copy` flag and `ui.js`'s first chip — because a reader paints its own pale blue highlight over every form field it finds and nothing inside the file can turn that off: an editable sheet reads as a page of blue boxes in Edge or Acrobat however the fields are coloured, which is what "there must be no blue boxes" was about. Neither copy draws a box on the page, so a hard copy of either reads as a spec sheet rather than a blank form, and the locked one is simply the same page with no field added. That cannot be left to reportlab: a field whose `fillColor` is `None` is not clear but filled in reportlab's own pale blue, and `forceBorder` painted that blue *into the page content* as well as into the field — fifty filled rectangles, one over each value, so a print path that leaves form fields out printed the boxes and not a single value, and every hard copy came out a page of blue boxes. `SPEC_FIELD_BOX` is therefore white and goes in as both the fill and the border, with no `forceBorder` at all; white rather than clear, because a field prints what somebody typed into it while the page underneath still carries the value as exported, and with nothing behind it the two print one across the other. `test_a_printed_spec_sheet_carries_no_box_around_a_value` pins the only two rectangles a spec page may paint — the sheet itself and the client band — and a `/MK` with no colour a printer can see, for both copies and both orientations. `spec_copy` validates the name the way `spec_orientation` does and an unknown one is a 400 through `app.copy_option`, because handing somebody a typeable sheet when they asked for a locked one is the mistake the option exists to prevent; the *editable* file is the one named `..._Editable.pdf`, since on paper the two are the same page and the working copy must not be the one sent out. Word and the CSV have no such choice — Word is a document to mark up and a CSV is text — so the dialog's PDF copy chips ride with the PDF link alone (`state.specCopy`, remembered in `localStorage` like the orientation). `test_workflow.test_the_pdf_goes_out_editable_or_locked_as_the_download_asks` pins both copies, the name and the refusal.
- The client deliverable is the approved finish schedule kept at `brand_assets/finish_schedule_template.pdf`: letter portrait, 46.8pt side margins, content 518.4pt wide, header rule at y=720, footer rule at y=44.64, flowing content between y=696 and y=56; Arial 9/10/10 for the code/item/description columns (50.4 / 144 / rest) with 6pt horizontal and 6.5pt vertical cell padding, leadings 13/13/13, `MIDDLE` cell alignment, and letter-spaced section headings 15.84pt tall whose rule starts 10pt after the text and ends `HEADING_OVERHANG` (6pt) past the right margin at x=571.2, matching the template. `test_workflow.ScheduleTests.test_layout_matches_the_approved_template` rebuilds that page and compares every text baseline and rule against the reference, normalising only the template's placeholder band values. The footer symbol is the one piece of that furniture the test cannot see, because an image is neither a baseline nor a rule: `mark_bottom` centres it on the contact line's cap middle (`FOOT_BASE` plus half the cap height) instead of standing it on the baseline, where it sagged below the words, and Word lowers its inline copy by the same offset with `w:position` over an at-least line so the symbol is not clipped. The contact line's own baseline and `CONTACT_X` are pinned by the template, so only the symbol may move. Keep that test green rather than eyeballing layout changes.
- `Unit Price` is an optional numeric Selections column; `put` writes `Qty` and `Unit Price` as real numbers so Excel's `SUM`/`ISNUMBER` work. The `Price Schedule` sheet (`price_schedule.rebuild`, run from `WorkspaceStore.save`) is a generated view, never an input: selections grouped by project then category with S.No, Code, Description, Qty, Unit Price and Price as live formulas against Selections, plus category subtotals, project totals and a grand total. Pricing is internal and must never appear in the client PDF, Word or PowerPoint copies; the spec sheets (`build_word.build_spec` and `build_lookbook.build_spec`, Word and PDF) are the only generated documents that show it.
- Client documents stay text only except one deliberate image: when a project's `Cover Image` holds an image, the exported PDF opens with a cover page (brand header, the rendering in a hairline frame, project and client centred below). Word, PowerPoint and fillable copies have no cover page. A `cover:<name>` cell value points at a file the app stored via `WorkspaceStore.store_cover`/`read_cover` — `./covers/` locally, `covers/` objects in the hosted bucket — set by `POST /api/projects/<pid>/cover` (PIL-normalised PNG/JPEG) and served back by the matching `GET`. URLs and file paths still work through `build_lookbook.resolve_cover`, which refuses non-public addresses before fetching. Product images stay internal review aids and there are still no closing pages. Keep row descriptions derived from workspace columns (manufacturer, product name or model, finish, quantity when not 1, client notes).
- Every schedule row that has a `Product URL` ends in a clickable `Product Link` — `build_lookbook.link_markup` for the PDF, a hyperlinked run in the PowerPoint and in Word, the same words in all three. This was requested deliberately and reverses the earlier "no hyperlinks in client deliverables" rule; only images and pricing remain internal. The fillable copies are the exception: their descriptions are editable fields compared against `description` on import, so a link there would read back as a hand-reworded line. `ui.js`'s paper preview appends the same link, and `rowDescription` must stay in step with `description` (which itself stays link-free, because `build_form`, `build_word` and `price_schedule` reuse it). `product_link` honours a hidden `Product URL` column.
- `Product Link` is a generated Selections column, never an input: `ensure_product_links` rewrites it on every save so the cell reads "Product Link" and hyperlinks to that row's `Product URL`, and `records` hides it so a workspace saved before the column existed reads back the same shape. Use the white/gold wordmark (`logo_path`) on dark backgrounds such as the app sidebar, the dark print wordmark (`logo_print_path`) on the white schedule pages, the gold symbol for compact branding, and always preserve aspect ratio.
